# 把闲置 Kindle 改成墨水屏看板：一次完整的踩坑记录

> 目标：用一台吃灰的 Kindle Paperwhite 3（KPW3，2015 款）做常显信息面板，
> 显示日期时间、天气和 MiniMax Token Plan 的额度消耗。
> 架构是「Linux 服务器渲染 PNG → Kindle 定时拉取 → eips 刷屏 → 深度休眠」。
>
> 这篇记录的是**真正卡住过的地方**，不是流水账。很多坑跟这个项目无关，
> 换任何老服务器 + 国内云 API 的组合都会再遇到一遍。

---

## 一、先说结论：六个最贵的坑

如果只能记住六条：

1. **MiniMax 国内站和国际站的凭证完全不互通**，跨区必定报 `invalid api key`
2. **CentOS 7 的 CA 证书太老**，HTTPS 下载会**静默失败**（下出 0 字节文件，不报错）
3. **官方/社区文档里的 API 响应结构可能是错的**，必须实测一次再写解析代码
4. **域名解析正常 ≠ 域名可用**。加了端口也可能被中间层拦截，
   报错却长得很像网络故障（`Connection reset by peer`）
5. **`eips` 只贴图不渲染**。图必须自己先转好方向和色深，
   否则会错位、被切、还会弹出软键盘（坑 14 / 15）
6. **百分比字段一定要标明「剩余」还是「已用」**。
   搞反了不是显示难看，而是把结论传达反了——满额度会显示成 0%（坑 20）

前三条花掉的时间最多，因为它们都不会给出明确的错误信息。
第 4 条是最容易误判的一条，详见坑 12.5。
第 5 条看起来最"低级"，但现象特别有迷惑性——你不会想到
"显示错乱"和"弹出键盘"是同一个原因。
第 6 条最隐蔽：数据、接口、渲染全都正常，只有**语义**错了。

> **另外有一条不属于"坑"，但最该一开始就想清楚**：
> 接管屏幕（停 framework）**就断了所有按键交互**，
> 必须提前设计退出路径，否则你每次都能把自己锁在里面（坑 21）。
> 这种"设计上的必然"比 bug 更值得先想到。
>
> 退出路径还要留**两条**：设备端自己听按键（坑 21）+ 服务端遥控（坑 22）。
> 后者有个反直觉的前提：**设备在深度休眠时收不到指令**，
> 所以只能"存下来等它醒"，而不是"点了立刻退"。
>
> **★ 还有一个"以为解决了、其实没解决"的教训（坑 21.8）**：
> 我一度以为"留 framework 就能保住电源键长按菜单"，
> 结果真机上长按毫无反应 —— 因为设备在 `echo mem` 深度休眠，
> suspend 状态下长按的语义是"唤醒"，不是"弹菜单"。
> **局部修复会被全局状态否决**；而且**"短按能用"推不出"长按也能用"**。

## 二、MiniMax Token Plan：三个连环坑

### 坑 1：2049 invalid api key，但 key 明明是对的

**现象**：拿的是正经的 Subscription Key（前缀 `sk-cp-`），调
`/v1/token_plan/remains` 却返回：

```json
{"base_resp": {"status_code": 2049, "status_msg": "invalid api key"}}
```

**原因**：MiniMax 有两套**完全独立**的基础设施，凭证不互通：

| | 平台 | API 域名 |
|---|---|---|
| 国际 | `platform.minimax.io` | `api.minimax.io` |
| 国内 | `platform.minimaxi.com` | `api.minimaxi.com` |

在国内平台拿的 key 去打国际域名（或反过来），一定失败。注意它的表现是
**HTTP 200 + 业务错误码**，不是 401，很有迷惑性。

**解决**：确认 key 是从哪个域名下的平台拿的，用对应区域的 API 域名。

**教训**：写探测脚本时，**业务错误也要换域名重试**。我最初只在网络不通时
才回退，结果跨区错误救不回来 —— HTTP 200 骗过了判断。

> 顺带一个快速判断 key 类型的方法：看前缀。
> `sk-cp-` 是 Subscription Key，`sk-api-` 是 pay-as-you-go 的 Key，
> 这个接口只认前者。

### 坑 2：真实响应结构和社区文档完全不一样

**现象**：拿到成功响应后发现，社区调研文档里推测的那套字段名根本不存在。

文档推测（错的）：

```json
{ "data": { "current_interval_total_count": 5000000, "current_interval_usage_count": 1245300 } }
```

实际返回（2026-09 实测）：

```json
{
  "model_remains": [
    {
      "model_name": "general",
      "current_interval_total_count": 0,          // 恒为 0，没用
      "current_interval_usage_count": 0,          // 恒为 0，没用
      "current_interval_remaining_percent": 100,  // ← 真正有效
      "end_time": 1790146800000,
      "current_weekly_remaining_percent": 99,
      "weekly_end_time": 1790524800000
    },
    { "model_name": "video", "...": "..." }
  ],
  "base_resp": { "status_code": 0, "status_msg": "success" }
}
```

三个差异：**没有 `data` 层**、额度按模型拆在 `model_remains[]` 里、
`total/usage_count` 恒为 0 而真正有效的是 `remaining_percent`。

**教训**：面对没有公开 schema 的接口，**先探测再写代码**。这一步省不掉，
我因为先写了解析代码、改结构后忘了同步探测脚本，还额外产生了一次误导性输出。

### 坑 3：双窗口制

Token Plan 有 **5 小时滚动窗口**和**周窗口**两个独立额度。滚动窗口的语义
和直觉不同：它是"过去 5 小时内用掉的量逐步归还"，**不是整点重置**。

做 UI 时得画两条进度条，只画一条会漏掉一半信息。

## 三、CentOS 7：Python 环境的四道关

服务器是腾讯云的 CentOS 7.9，自带 Python 3.6.8 + pip 9.0.3。

### 坑 4：Python 3.6 跑不了现代代码

**现象**：`pip install -r requirements.txt` 报
`No matching distribution found for Flask>=3.0.0`，索引里最高只有 Flask 2.0.3。

**原因**：Python 3.6 太老。项目用了 `from __future__ import annotations` 和
`dataclasses`，两个都要 **3.7+**。

**为什么选择装新 Python 而不是改代码兼容 3.6**：改代码要动一堆类型注解，
而且 Pillow 新版也不支持 3.6，会连锁降级。**装个新 Python 更干净**。

### 坑 5：EPEL 只有 python36，IUS/SCL 已失效

CentOS 7 在 2024-06 已 EOL，`yum list available | grep python3` 里只有
`python36*`。IUS 源停止了 EL7 支持，`/opt/rh`（SCL 目录）是空的。

### 坑 6：Miniconda 最新版要 GLIBC ≥ 2.28

**现象**：装 Miniconda 时直接报

```
Installer requires GLIBC >=2.28, but system has 2.17.
```

**原因**：CentOS 7 的 glibc 是 2.17，新版本构建时要求 2.28。

**解决**：换**老版本** Miniconda。2022 年的
`Miniconda3-py39_4.12.0-Linux-x86_64.sh`（76 MB）明确支持 glibc 2.17。

### 坑 7：CA 证书太老，HTTPS 下载静默失败 ★最坑

**现象**：`wget -q <url> -O /tmp/x.sh` 跑完没报错，但文件是 **0 字节**。

**原因**：CentOS 7 的根证书太老，验证不了新站点的证书，TLS 握手失败。
而 `wget -q` 把错误吃掉了。

**解决**：跳过证书校验（下载公开安装包时风险可接受）：

```bash
curl -sSLk -o /tmp/mc.sh <url>     # curl 用 -k
wget --no-check-certificate <url>  # wget 用这个
```

加了 `-k` 之后清华镜像一次就下到了 198 MB。

**教训**：
- 下载遇到 0 字节，**先怀疑证书问题**，别急着换镜像
- 调试期**不要用 `-q`**，静默模式会藏掉真正的错误
- 顺带一个判断技巧：下载的文件只有几 KB，基本就是错误页（真安装包几十 MB 起）

> 华为云镜像的 anaconda 路径下没有 Miniconda，返回的是 12 KB 错误页。
> 清华源的路径是好的。

## 四、配置与部署

### 坑 8：YAML 缩进

**现象**：手改 `config.yaml` 后报

```
yaml.parser.ParserError: expected <block end>, but found '<block mapping start>'
```

**原因**：YAML 只认**空格**缩进，vi 里按 Tab 或者块位置错位都会炸。

**解决**：别手改，用 heredoc 整份覆盖（还能顺便自动探测字体路径）：

```bash
FP=$(ls /usr/share/fonts/wqy-zenhei/*.ttc 2>/dev/null | head -1)
cat > config.yaml << EOF
fonts:
  regular: "$FP"
...
EOF
```

### 坑 9：systemd 的 Environment 优先级高于 .env ★

**现象**：`.env` 里的 key 是干净的（诊断脚本确认过），但页面一直报
`'latin-1' codec can't encode characters`。

**原因**：两件事叠加：

1. 加载逻辑是「真实环境变量 > `.env`」，所以 systemd 里设的值会**覆盖** `.env`
2. 我把模板里的**中文占位符原样复制**进了 systemd 配置：
   `Environment=MINIMAX_SUBSCRIPTION_KEY=你的SubscriptionKey`

于是服务拿中文去当 Bearer token —— HTTP 头不能有非 ASCII 字符，直接编码失败。

**解决**：删掉那行，让服务读 `.env`：

```bash
sed -i '/^Environment=/d' /etc/systemd/system/kindle-dashboard.service
systemctl daemon-reload && systemctl restart kindle-dashboard
```

**教训**：
- 给别人的配置模板，**占位符别用中文**，太容易被原样复制
- 更好的做法是代码启动时检测关键环境变量是否仍是占位符，直接报明确错误
- 排查"配置没生效"时，先确认**到底有几处能设置同一个值**，以及它们的优先级

### 坑 10：FirewallD 根本没运行，但端口还是不通

**现象**：`firewall-cmd --list-ports` 返回 `FirewallD is not running`，
但浏览器死活打不开。

**原因**：云服务器的**安全组是独立于系统防火墙的一道闸门**，而且优先级更高。
系统里敲什么命令都没用，必须在云平台控制台放行。

**解决**：腾讯云控制台 → 安全组 → 入站规则 → 放行 TCP 8787。

**教训**：云服务器端口不通，排查顺序应该是：**安全组 → 系统防火墙 → 服务本身**。
安全组是最容易漏的一步。

### 坑 11：systemd 启动 failed —— 端口冲突 ★而且会伪装成"代码有问题"

**现象**：先手动 `nohup` 起了服务（所以能访问），再配 systemd 就 failed。

**原因**：手动进程占着 8787，systemd 再启一个实例撞端口。

```bash
pkill -f "main.py"
systemctl start kindle-dashboard
```

**但这个坑远比看上去阴险**，因为它会**伪装成"你刚改的代码有问题"**。
真实日志长这样：

```
INFO dashboard: 渲染自检通过: 1072x1448 L     ← 代码跑得好好的
INFO dashboard: 监听 http://0.0.0.0:8787
Address already in use                        ← 唯一的问题在这
Port 8787 is in use by another program.
systemd[1]: main process exited, code=exited, status=1/FAILURE
systemd[1]: start request repeated too quickly
```

如果你**只看了 systemd 的摘要**，看到的是：

```
Active: failed (Result: start-limit)
Process: 13691 ExecStart=... (code=exited, status=1/FAILURE)
```

`status=1/FAILURE` + "刚改完代码就崩了" —— 很容易得出
"是我这次的改动把服务搞崩了"的错误结论，然后开始翻代码、查依赖版本，
**方向全错**。而真正的原因（端口占用）就明明白白写在应用日志里。

**两个关键教训**：

1. **`journalctl` 要看应用自己的 stdout，不能只看 systemd 几行摘要。**
   应用层的日志才是第一现场：
   ```bash
   journalctl -u kindle-dashboard -n 50 --no-pager   # 别只 head 前 10 行
   ```
   摘要里的 `status=1/FAILURE` 只说明"进程退出了"，**不说明为什么**。

2. **端口冲突必须用 `reset-failed` 解开。**
   连续崩几次后 systemd 会熔断（`start-limit`），此时
   `systemctl restart` 会被**直接拒绝**，连试都不试：
   ```bash
   ss -lntp | grep 8787              # 看是谁占着
   pkill -f "main.py"                # 清掉野进程
   ss -lntp | grep 8787              # 确认已释放
   systemctl reset-failed kindle-dashboard   # ★ 解除熔断
   systemctl restart kindle-dashboard
   ```

**预防**：不要混用"手动 nohup"和"systemd"两种启动方式。
调试时可以用前台运行（`Ctrl+C` 就能干净退出），
但别后台 nohup，否则很容易留下一堆看不见的野进程。

### 坑 12：时区

**现象**：（预防性发现）服务器时区经常是 UTC，`datetime.now()` 显示会差 8 小时。

**解决**：按配置里的时区取时间：

```python
from zoneinfo import ZoneInfo
dt.datetime.now(ZoneInfo(cfg["location"]["timezone"]))
```

### 坑 12.5：域名能用 ≠ 加了端口还能用 ★反直觉

**现象**：服务器 IP 直连 `http://YOUR_SERVER_IP:8787` 完全正常（200 OK），
换成域名 `http://your-domain.example.com:8787` 就拉不到图。
Kindle 端报的是：

```
Connecting to your-domain.example.com:8787 (YOUR_SERVER_IP:8787)
wget: error getting response: Connection reset by peer
```

**第一反应**会是"网络问题"或"Kindle 的 WiFi 有问题"——**都错**。
DNS 是通的（`nslookup` 解析出 `YOUR_SERVER_IP`，就是服务器 IP），
TCP 也连上了，`Connection reset` 是被中间的拦截层重置的。

**真相**：`curl -i` 一看就明白：

```
HTTP/1.1 302 OK
Location: https://dnspod.qcloud.com/static/webblock.html?d=your-domain.example.com:8787
```

请求被 **302 重定向到拦截页**，压根没到服务器。
有意思的是 Kindle 的 wget 日志里其实已经泄了底：
`Connecting to dnspod.qcloud.com (114.117.133.49:443)` ——
它跟着 302 跑去访问拦截域名了。

**教训（可复用的排障手法）**：
- 报错是 `Connection reset` / `Connection refused` 时，**先 `curl -i` 看一眼有没有 302**，
  别急着怀疑网络
- 判断"是域名的问题还是服务器的问题"，做个**对照实验**：
  同一个端口，IP 直连 200、域名 302 → 跟服务器和网络都无关，是 **Host 维度被拦**
- **解析正常不代表可用**。DNS 只负责把名字翻译成 IP，翻译对了，
  后面的拦截它管不着

**结论**：设备端老老实实用 IP 直连。想要域名，得先确认域名本身
（备案状态、是否被安全网关标记）没问题。
这个坑对国内云服务器 + 个人域名是高频场景。

## 四·五、接管屏幕之后：退出路径的两个坑

看板跑起来以后，真正的麻烦才开始 —— **你把自己锁在设备外面了**。

### 坑 21.5：不是所有电源键都叫 KEY_POWER，也不是所有按键都暴露给用户态

**现象**：退出看板的方案是「后台起一个看门狗，监听 `/dev/input/eventX`
上的电源键长按事件」。代码写完、本地测试全过、逻辑也没问题，
但**在真机上按电源键就是没反应**。看门狗日志里只有一行：

```
!! 没匹配到电源键设备，以下是全部候选：
   候选: /dev/input/event0  name=max77696-onkey
   候选: /dev/input/event1  name=cyttsp4_mt
看门狗无法工作（没找到电源键设备）
```

**排查过程**：

第一反应是"设备名匹配规则太窄"。当时的规则是匹配
`gpio-keys` / `power` / `button` 这些关键词，
而 `max77696-onkey` 里确实**没有**这些词 —— 看起来就是漏了个规则。

于是加了**第二轮匹配：不看名字，改读能力位图**。
`/sys/class/input/eventN/device/capabilities/key` 是一个十六进制位图，
第 N 位为 1 就代表支持 keycode N。既然键盘能力精确对应到 keycode，
那"谁声明支持 `KEY_POWER`(116)，谁就是电源键设备"，应该稳了。

结果第二轮**也没匹配上**。

**★ 关键认知（这才是真正的坑）**：

`max77696-onkey` 是 KPW3 的电源键设备（名字里的 `onkey` 就是它），
但它的 `capabilities/key` 位图里**根本没有第 116 位**。

也就是说：**内核把这个设备的按键上报，走了另一套路径**
（很可能是 `input_set_capability` 之外的私有通路，
或者压根不通过标准 input 事件暴露给用户态）。

推论很硬：

- **按名字匹配** —— 靠猜名字，`onkey` 不在词表里就漏
- **按能力位图匹配** —— 位图里没声明，再准的判定逻辑也判定不出来
- 两条路都堵死 → **这个按键事件在用户态就是看不见的**

**教训**：

1. **"设备支持某个功能"和"这个功能对用户态可见"是两件事。**
   位图是内核声明，不是用户态保证。别把位图当成"肯定能读到"的凭据。
2. **匹配规则要分两轮，但两轮都可能失败，所以要留"诊断模式"。**
   最终给脚本加了 `diag` 子命令：一次列出所有 event 设备、
   完整按键位图、以及对常见电源键码（`KEY_POWER`=116 /
   `KEY_POWER2`=174 / `KEY_SLEEP`=142 / `KEY_WAKEUP`=143）
   逐个判定"本机有没有设备支持"。
   把这台机器**到底能听到什么**一次说清楚，而不是反复猜。
3. **别在"猜规则"上耗轮次。** 正确地做一次穷举诊断，
   比加十条名字匹配规则都有用。
4. **失败要给出可行动的下一步。** 看门狗发现匹配不上时，
   不能只是静默死掉 —— 日志里写清"可改用 `;log stopdash` 手动退"，
   并且诊断模式明确告诉你"这条路走不通，用服务端遥控"。

**所以最终的双通道设计是必要的，不是冗余**：

| 通道 | 依赖 | 在本机上的状态 |
|---|---|---|
| 长按电源键（设备端） | 按键事件对用户态可见 | ❌ 本机不可用（见上） |
| 网页点「退出看板」（服务端遥控） | 网络 + token | ✅ 已验证可用 |
| 搜索框 `;log stopdash` | 系统级输入通道 | ✅ 已验证可用 |

如果一条路都没做，这时候就真的只能长按电源键强制重启了
（且看板在跑时它还在深度休眠，长按只会唤醒、不会重启）。

> 反过来说：**"加了冗余方案"和"知道哪条路真的通"是两件事。**
> 冗余方案的意义在于，当主路径因为这种"设计上就不可能"的原因
> 失效时，你还有得退。但**必须实测确认备路径真的通**，
> 否则你以为自己有两条路，其实两条都没走过。

### 坑 21.6：管道右侧的 `while` 在子 shell 里，`exit` 退不出去

**现象**：看门狗日志里明明白白写着「长按达标 → 退出看板」，
但**屏幕没变**，原生界面也没回来。

**根因**：最直观的写法是错的，而且错得很隐蔽：

```sh
# ❌ 这样写，exit 0 只结束子 shell
od -An -tu1 -w16 "$DEV" | while read -r LINE; do
    ...
    exit 0        # 子 shell 里！外层 while true 会 sleep 1 后重连
done
```

管道 `|` 会让右侧的 `while` 跑在**子 shell** 里。
子 shell 里的 `exit 0` 只结束它自己，
外层「断线重连」的 `while true` 会接着往下走、
`sleep 1`、重新 `od` 监听 —— 看门狗**复活**了。

现象极具迷惑性：**日志说"已退出"，屏幕却还是看板**。

实测（POSIX sh）：

```sh
$ sh -c 'echo x | while read L; do exit 0; done; echo alive'
alive                          # exit 根本没生效
```

**试过但放弃的方案**：FIFO（`od > fifo &` + `while read < fifo`）。
它能避开管道子 shell，但 FIFO 的打开/EOF 语义很讲究 ——
写端一断读端就 EOF，下次打开又**阻塞等写端**。
在"od 意外退出要重连"这种场景下容易卡死在第二轮打开上。

**最终方案**（语义最确定）：

```sh
# ✅ od 后台阻塞读设备，输出追加到事件文件
od -An -tu1 -w16 "$DEV" >> "$EVFILE" 2>/dev/null &
OD_PID=$!

# 主 shell 轮询文件行数增量，逐行解析
while true; do
    TOTAL=$(wc -l < "$EVFILE")
    if [ "$TOTAL" -gt "$LAST" ]; then
        _new=$(sed -n "$((LAST+1)),${TOTAL}p" "$EVFILE")
        LAST=$TOTAL
        while read -r LINE; do
            ...
            exit 0        # ✅ 在主 shell 里，真的能退出
        done <<EOF
$_new
EOF
    fi
    ...
done
```

好处：
- 解析全程在**主 shell** → `exit` 真生效
- 没有阻塞语义 → 不会卡死
- `od` 依然阻塞读字符设备 → 没按键时几乎不耗 CPU
- （拿 `sleep 1` 的轮询开销换确定性，很划算）

**改成 heredoc 是关键**：`while read` 的输入用 `<<EOF` 而不是管道，
循环体就留在主 shell 里。

**这个坑的普适价值**：**"日志说成功了"不等于"真的成功了"。**
`exit` 在子 shell 里静默失效，是所有 shell 脚本里最经典的
"看起来对了但没生效"之一。任何写 `cmd | while ...` 的地方，
只要循环体里有 `exit` / 变量赋值要在循环外使用，都要条件反射地检查。

### 坑 21.7：事件文件"重连时清空"会丢事件

顺着上一坑改方案时，顺手写了「每次重连清空事件文件、把行号归零」。
**这是错的**：

```
od 刚写入事件 → （还没被轮询读到）→ 重连逻辑清空文件 → 事件永久丢失
```

在 PC 上用普通文件测时必现 —— `od` 读完普通文件就 EOF 秒退，
重连极其频繁，清空那一刻的事件直接没了。
表现就是**"短按/长按都没反应"**。

**修法**：**只追加不截断，`LAST` 只增不减**。
代价是文件会涨，用**定期瘦身**控制：
攒够 `EV_TRIM_LINES` 行就砍掉已解析的部分，只留最后若干行。

```sh
if [ "$LAST" -gt "$EV_TRIM_LINES" ]; then
    _tail_keep=$((EV_TRIM_LINES / 2))
    [ "$_tail_keep" -gt 200 ] && _tail_keep=200
    [ "$_tail_keep" -lt 10 ] && _tail_keep=10
    _keep_from=$((LAST - _tail_keep + 1))
    sed -n "${_keep_from},\$p" "$EVFILE" > "$EVFILE.trim" &&
        cat "$EVFILE.trim" > "$EVFILE"
    LAST=$_tail_keep
fi
```

注意两点：
- 保留量取 `min(200, EV_TRIM_LINES/2)`。写死 200 的话，
  测试把阈值调到 40 时会出现"砍完还剩 200 行、仍超阈值"的自我打架。
- 先写临时文件再整体覆盖（不能直接重定向到 `$EVFILE`，那会先清空它，
  正好犯了要避免的错）。

**普适原则**：**"事件流的消费者"不能用"清空"来重连。**
任何"生产者写文件、消费者读文件"的结构，重连时都要保证
"只前进、不回退"，否则一定会丢数据。

### 坑 13：越狱 ≠ 安卓

这是最容易被误导的一点。KPW3 越狱后**拿到的只是 root shell**，
里面没有 Android 运行时，**装不了任何 `.apk`**。

所以想在 KPW3 上跑 Obsidian（Electron 应用）是不可能的，硬件也不够
（i.MX6SL + 512 MB RAM）。网上"KPW3 刷安卓双系统"的说法不可信。

真正的需求如果是「墨水屏上看 Obsidian 笔记」，可行路径是
**KOReader 直接读 `.md`**（只读，双链/Dataview 失效），
或者干脆用安卓墨水屏设备（文石 Boox 等）。

### 坑 14：分辨率别照抄 —— 而且「横屏图」是画完还要转的 ★

KPW3 是 **1448 × 1072 / 300ppi / 16 级灰度**。
网上大量教程写 758×1024，那是 Paperwhite 1/2 的，照抄会画面错位。

但这里有个更隐蔽的第二层：**照片的「1448×1072」和 framebuffer 的
「1448×1072」不是一回事。** 实测 `eips -i` 的输出是：

```
xres: 1072          yres: 1448
bits_per_pixel: 8   grayscale: 1
xres_virtual: 1088  rotate: 3
```

**framebuffer 其实是 1072 宽 × 1448 高的竖屏。**
而 `eips -g` 做的事只有一件：把图片按**行优先**原样贴到显存起点，
**它没有任何旋转参数**（官方 wiki 上全部选项只有 `-g -b -w -f -x -y -v`）。

于是送一张 1448×1072 的图过去，会被当成「宽度只有 1072」来解读，后果是：

- 图片右边被切掉
- 内容整体错位，看起来像「竖屏版本」
- **framework 被惊动，屏幕上弹出输入框和软键盘**，把画面盖住

**正确做法**：在横屏画布（1448×1072）上正常布局，**输出前做两步变换**：

```python
img = img.transpose(Image.Transpose.ROTATE_90)   # 90° 逆时针 → 1072×1448
img = img.convert("L")                            # 8 位灰度，色深也要匹配
```

转完尺寸正好是 1072×1448，和 framebuffer 完全一致，贴上去就是正的横屏。

**两个必须注意的点**：
- **方向是逆时针**（`ROTATE_90`）。用顺时针（`ROTATE_270`）内容会上下颠倒
- **色深也要管**：framebuffer 是 `bits_per_pixel: 8` + `grayscale: 1`，
  所以必须转成 8 位灰度 PNG。有项目就是因为送了 1 位灰度图而显示异常

**教训**：`eips` 是「贴图」不是「渲染」。它不会帮你缩放、旋转、转色深，
**你给什么它就贴什么**。任何方向的适配都得在服务器端做完。
判断依据直接问设备：`eips -i` 会告诉你确切的 framebuffer 参数。

### 坑 15：屏幕上冒出软键盘，是因为 framework 没停干净 ★

**现象**：看板刷出来了，但触摸屏幕就弹出输入框和软键盘，把画面盖住。

**原因**：Kindle 原生 UI（framework）还活着，它检测到触摸就按正常逻辑弹输入法。

**关键**：**只停 `framework` 不够**，KPW3 上还挂着 `lab126_gui` 和 `webreader`。
参考 `pascalw/kindle-dash` 的 `init()`，要停的是一整套：

```sh
initctl stop lab126_gui        # ★ 最容易漏的就是这个
initctl stop framework
initctl stop webreader
/etc/init.d/framework stop     # 老式 init 脚本，两条路都试

# 键盘本身是独立进程，光停 framework 有时压不住
lipc-set-prop -s com.lab126.keyboard close ::

# 顺手省电
echo powersave > /sys/devices/system/cpu/cpu0/cpufreq/scaling_governor
lipc-set-prop com.lab126.powerd preventScreenSaver 1
```

**两个容易踩的细节**：
- 停完要 **`sleep 3` 等 UI 真正退干净**再刷图，
  否则可能出现「刷完了被最后残留的一帧盖掉」
- **休眠唤醒后 framework 可能被系统重新拉起**，
  所以每轮循环都重新压一次，别只在启动时做一次

恢复时记得把 `preventScreenSaver` 设回 0、framework 三件套重新 start，
不然退出看板后设备会一直停在无 UI 状态。

### 坑 16：nginx 报 502 但 curl 不报错，别被 `file` 静默失败骗了

**现象**：改完代码重启服务，想验证一下——

```bash
curl -s -o /tmp/t.png http://127.0.0.1:8787/dashboard.png && file /tmp/t.png
# （什么都不输出，回到提示符）
```

看着像"命令成功但没打印"，很容易误判成"图片渲染有问题"。

**真相有两层**：

1. **`file` 在 CentOS 7 的 minimal 环境里经常没装**，会静默失败（命令不存在），
   所以你什么也看不到。**验证 PNG 尺寸别依赖 `file`**：
   ```bash
   # 看前 33 字节就够（PNG 头里的宽高在第 16-24 字节）
   xxd -l 33 /tmp/t.png | head -3
   ```
   或者更省事，直接看 HTTP 状态码。

2. **实际是 502**：`curl` **没加 `-f` 时不会因为 4xx/5xx 而报错**
   （exit code 仍是 0），下载到的其实是 nginx 的 502 HTML 错误页。
   `-s` 又把进度和错误信息都吞了。所以"命令成功了"是假象。

**排障口诀**：验证服务可用性时，**永远看状态码**：
```bash
curl -s -o /tmp/t.png -w "HTTP %{http_code}  %{size_download} bytes\n" \
     http://127.0.0.1:8787/dashboard.png
```
502 就说明服务根本没起来，跟图片本身无关。

> ⚠️ **端口别记错**：Flask 服务监听的是 **8787**（见 `config.yaml` 的 `server.port`），
> 日志里也会自己报 `监听 http://0.0.0.0:8787`。
> `HTTP 000` 通常不是"服务没起"，而是**你连了一个没有东西监听的端口**——
> 先用 `ss -lntp | grep 8787` 确认端口，再判断服务死活。

### 坑 18：`HTTP 000` 有两种含义，先分清再排查

`curl` 返回 `HTTP 000` 时，很多人第一反应是"服务挂了"。其实它表示
**连接根本没建立**，常见两种原因，排查方向完全不同：

| 情况 | 判断方法 |
|---|---|
| 服务真没起 | `ss -lntp \| grep 8787` 无输出 |
| **端口写错了** | 端口是空的，但服务在别的端口上跑得好好的 |

第二种特别容易发生：**顺着文档里的命令一路复制，而文档里的端口是错的**——
于是你会花大量时间去查一个根本不存在的问题。
（这个坑是真实的：本轮排查中，验证命令里的端口就被写成了 `8789`，
而服务实际在 `8787`，导致白白绕了一圈。）

**习惯**：报错时先确认"我测的对象对不对"，再怀疑"东西坏没坏"。
`ss -lntp` 一行就能给出答案，比读日志还快。

### 坑 17：Pillow 版本下限放太宽，新写法直接让服务起不来

**现象**：本地渲染一切正常（本地 Pillow 12），
部署到服务器后 `systemctl restart` 成功、`systemctl status` 也不报错，
但 nginx 一律 502。

**原因**：`requirements.txt` 里写的是 `Pillow>=8.0.0`，
而代码用了 `Image.Transpose.ROTATE_90` ——
**这个枚举是 Pillow 9.1 才引入的**。
服务器上装的是老版本 Pillow，属性不存在 → `AttributeError` →
进程启动即崩 → 没有进程监听端口 → nginx 502。

**关键教训**：`>=` 的下限和实际用到的 API 必须对齐。
用了个"较新但不算太新"的 API，而依赖写得很宽松，就会出现
**本地好、服务器崩**的分裂现象。

**修法**：改用**常量值**，绕开枚举存在性的问题：

```python
img.transpose(2)   # 2 == Image.ROTATE_90（逆时针），Pillow 8/9/10/11/12 都认
img.transpose(3)   # 3 == Image.ROTATE_270
```

**顺带一个通用做法**：在服务启动时做一次**渲染自检**，
失败就大声报错 + `raise`。否则你看到的只是"502 但没有日志指向原因"，
要从 nginx 一路倒推回 Python 异常。

### 坑 19：电量不显示 —— 一个 bug 的两个独立成因

看板上「右上角显示 Kindle 电量」，但实际没显示。查下来是**两个互不相干**的 bug 叠加，
任何一个单独存在都会导致电量缺失。

**成因 A：设备端拿不到电量（更根本）**

原来只试了一种取法：

```sh
lipc-get-prop com.lab126.powerd battLevel    # ❌ KPW3 上常常返回空
```

**这个属性名各机型/固件不一样，KPW3 上经常取不到。**
而且取不到时脚本会退化成传 `batt=0`，服务端老老实实画一个 **0% 的电池图标** ——
比"没显示"更误导人。

修法：**依次尝试三种取法**，取到空就换下一种，全都失败才隐藏电量区：

```sh
# 1) lipc 属性（部分固件有）
lipc-get-prop com.lab126.powerd battLevel
# 2) gasgauge-info —— KPW3 上更可靠
gasgauge-info -c | tr -cd '0-9'
# 3) sysfs 兜底
cat /sys/class/power_supply/*/capacity
```

关键点：**取不到就返回空、不要传 0**，让服务端隐藏电量区，
而不是画一个假的 0%。

**成因 B：服务端缓存把电量"冻住"了（更隐蔽）**

```python
# ❌ 只按时间判断缓存
fresh = _png_cache is not None and (time.time() - _png_stamp) < cache_secs
if fresh:
    return Response(_png_cache)      # 直接返回旧图，新电量被忽略
```

`cache_secs` 默认 120 秒。在这 120 秒内，不管设备上报什么电量，
**返回的都是同一张旧图** —— 电量看起来永远不变，或者一直是空。

**这是"缓存忽略了请求参数"这类 bug 的典型形态**：
缓存键不完整 → 不同参数的请求互相污染。

修法：**把电量并进缓存键**，电量变了就让缓存失效：

```python
batt_key = -1 if battery is None else battery // 5   # //5 分桶，避免1%抖动就重渲染
fresh = (
    _png_cache is not None
    and (time.time() - _png_stamp) < cache_secs
    and _png_batt_key == batt_key        # ★ 电量不同 → 缓存失效
)
```

**教训（可复用）**：

1. **缓存的键必须覆盖所有会影响输出的输入。**
   只要某参数会改变渲染结果，它就必须进缓存键。
   漏了就会出现"某块内容永远不更新"的怪现象 ——
   而且**特别难查**，因为代码逻辑看起来完全正常。
2. **取不到数据时，要"隐藏"而不是"填 0"。**
   `batt=${BATT:-0}` 这种写法很自然，但会把"未知"伪装成"确定值"，
   画出误导性的 0%。同理适用于任何可选的展示字段。
3. 排查"某块内容不显示"，**先分清是"没取到数据"还是"没渲染/没传出去"**：
   服务端单独渲染一张带值的图（本地就能做），
   如果正常，问题就在数据获取或缓存，不在渲染。

### 坑 20：额度进度条满格却是 0% —— 「剩余/已用」语义搞反 ★

看板上 MiniMax 两条额度条**一直是空的、数字显示 0%**，看着像"额度用光了"。
但实际上是**满额度**。查 `/debug.json`：

```json
{"label":"5小时","limit":null,"remaining":null,"percent":0.0,
 "reset_at":"2026-09-28T15:00:00"}
```

`reset_at` 能拿到 → 说明字段名对得上、API 调通了；
`percent` 是 0 → 说明**取到了值，只是算错了**。

抓真实响应一看就明白了：

```json
{"model_name":"general",
 "current_interval_remaining_percent":100,
 "current_weekly_remaining_percent":100}
```

上游给的是 **`remaining`（剩余）= 100**，而解析代码做了翻转：

```python
percent_given=100.0 - iv_rem     # ❌ 100-100 = 0
```

于是"剩余 100%"被算成"已用 0%"，进度条画了个空条。

**为什么会写成 `100 - x`？** 因为一开始把 `percent` 定义成了"已用百分比"，
以为上游给的是"剩余"，所以要翻一下。**但翻的方向取决于上游字段的语义，
而字段名里的 `remaining` 其实已经说清楚了。**

**修法不是简单地把 `100 -` 去掉，而是把语义统一**：

```python
# Window 统一口径：percent 表示「剩余」
@property
def percent_remaining(self):
    if self.percent_remaining_given is not None:
        return self.percent_remaining_given       # 上游给的就是剩余，直接用
    if self.used is None or not self.limit:
        return None
    return (self.limit - self.used) / self.limit * 100.0
```

同时把字段名从 `percent_given` 改成 **`percent_remaining_given`** ——
名字里带 `remaining`，下次谁看都不会再搞反。

再在进度条右边加一个「剩」字，人眼扫一眼就知道方向：

```
剩 62%  ████████████░░░░░░░░
剩 18%  ███░░░░░░░░░░░░░░░░░
```

**教训（可复用）**：

1. **百分比一定要在字段名里写清是「剩余」还是「已用」。**
   `percent` 这种中性名，早晚会被自己或者同事搞反。
2. **上游字段名往往已经暗示了语义，别急着翻转。**
   看到 `remaining_percent` 就直接当剩余用；要翻转，先确认上游真的是另一种。
3. **额度看板：口径必须唯一，而且条和数字要一致。**
   当时选的是「剩余」—— 满额 = 满条。因为空条配 0% 的语义
   等于"没额度了"，正好把结论传达反了。
   这是**可用性问题，不是纯显示问题**。

   > **【后续调整】** 后来按实际使用习惯改成了**画「已用」**：
   > 用掉的填黑、还剩的留白，数字旁边标一个「用」字。
   > 方向变了，**但教训没变** —— 条和数字必须是同一个口径，
   > 并且把这个口径**写在界面上**（「用」/「剩」那个字就是干这个的）。
4. 排查"数值不对"，**先把原始响应打出来**。
   `limit=null 但 reset_at 有值` 这个组合就是很强的线索：
   说明解析路径走通了，只是某个字段名没匹配上或算错了。

### 坑 21：看板跑起来后，人被"关"在里面出不去 ★

**现象**：`;log runme` 启动看板后，电源键、触摸全都没反应，
只能长按电源键强制重启才能回主界面。
（更糟的是：**连"主动重启"都做不到** —— 长按短按都没反应。）

**原因**：不是 bug，是**必然结果**。

看板为了独占屏幕，停掉了 `framework` / `lab126_gui` / `webreader`
（坑 15）。而 **Kindle 的电源键短按事件恰恰是 framework 在处理** ——
framework 停了，按键事件就没有应用层去响应了。
`preventScreenSaver 1` 还让设备不进屏保，等于把自己锁在画面里。

我搜到一个国外老哥做同样的事，最后的结论是：

> "Except for one: the power button. If the dashboard is running,
> I can use the power button to reboot the Kindle."
> —— 他最后也只能靠**重启**出来。

---

#### 第一版解法（失败）：绕开 framework，直接读内核按键事件

关键认知：**framework 只是"消费者"，内核的输入子系统一直在工作。**
按键事件照样写进 `/dev/input/eventX`，谁读谁就能知道。

32 位系统上每条事件 16 字节：

```
offset 0-7    time  (sec + usec)
offset 8-9    type  (EV_KEY = 1)
offset 10-11  code  (KEY_POWER = 116)
offset 12-15  value (1=按下 0=松开)
```

用 `od` 转成十进制文本后，字段落在第 **9** / **11** / **13** 个位置：

```sh
od -An -tu1 -w16 /dev/input/eventX | while read -r LINE; do
    set -- $LINE
    [ $# -lt 13 ] && continue
    EV_SEC=$1; TYPE=$9; CODE=${11}; VAL=${13}
    [ "$TYPE" = 1 ] && [ "$CODE" = 116 ] || continue
    ...
done
```

**三个技术点确实是对的**（保留在这里，将来做别的输入处理还用得上）：

1. **`-w16` 不能省**。不加的话 `od` 按自己的列宽换行，
   一条 16 字节的事件可能被拆到两行，字段位置就全错了。
2. **字符设备会阻塞，这是好事**。`/dev/input/eventX` 是字符设备，
   `od` 读它会**阻塞等待**，没按键时脚本静静睡着，几乎不耗 CPU。
   **别改成轮询普通文件** —— 那会变 100% CPU 忙循环。
3. **用事件自带时间戳算长按，别用 `date +%s`**。
   事件结构体的 offset 0-7 就是内核打的 `time.tv_sec`（`od` 输出的
   **第 1 个字段**）。用它是"事件真实发生的时刻"；
   用 `date +%s` 是"读到这条事件的时刻"，会被缓冲/读取延迟污染，
   实测能算出 0 秒这种离谱结果。

**但整个方案在 KPW3 上是不可行的 —— 见坑 21.5。**
真机日志给出硬证据：这个电源键的按键事件**在用户态根本看不见**。
按名字匹配、按能力位图匹配两条路都堵死。

---

#### 最终解法（可行）：把电源键还给系统

**根因不在"怎么读按键"，而在"为什么要抢按键"。**
抢按键是被迫的 —— 因为我们为了独占屏幕停掉了 framework，
而**电源键是 framework 在管**。那就**别停 framework**。

改成**只停 `lab126_gui` + `webreader`，保留 framework**：

| 停掉 | 作用 |
|---|---|
| `lab126_gui` | 主页/界面层 → 停掉它，主页就不会盖看板 |
| `webreader` | 浏览器组件 → 少一个抢屏的 |
| ~~`framework`~~ | **留着** → **短按电源键（休眠/唤醒）可用**<br>（注意：**长按的菜单并不会因此可用**，见坑 21.8） |

于是：

- **短按电源键** → 系统正常休眠 / 唤醒
- **长按电源键** → ⚠️ **看板运行时弹不出菜单**（见坑 21.8），
  必须**先退出看板**回原生界面，长按才有「重启/取消/熄屏」菜单
- **退出看板** → 网页「退出看板」按钮 / `;log stopdash`（两条都验证过）

代价：framework 活着，戳屏幕时它仍可能弹输入框/软键盘。
但看板是放着看的、不会天天去戳，这个代价可以接受。

> **★ 校正（2026-09-28 下午，真机实测）**：
> 上面"长按 → 弹重启菜单"这个结论**是错的**。
> 只留 framework 并不能让长按弹出菜单 —— 因为还有第二层原因，
> 而且那一层比 framework 更根本。详见**坑 21.8**。
> 当时我看到"短按能用"就以为"长按也能用"，**验证不充分就下了结论**。

**教训（可复用）**：

1. **"停掉上层服务"等于"放弃它提供的所有交互"。**
   接管屏幕前先想清楚：**用户怎么出来？**
   任何"独占"式设计都必须配一条退出路径，否则就是把人锁在里面。
   （同理适用于 kiosk 模式、全屏应用、单用户模式……）
2. **★ 遇到"某个功能失灵"，先问"这个功能原来归谁管"。**
   电源键失灵不是电源键坏了，是**它的管理者被我们停了**。
   与其想办法绕过管理者（自建监听），不如**把管理者留下** ——
   后者往往一行改动就够，前者要重写一遍子系统还未必成功。
3. **★ 权衡时要看清"代价换的是什么"。**
   停 framework 换来的是"屏幕上绝对不会有原生 UI 冒出来"，
   代价是"所有按键失灵、无法重启"。
   前者靠只停 `lab126_gui` 就能拿到八成的效果，
   后者却是硬伤 —— 这笔账一开始就该算清楚。
4. **上层停掉 ≠ 底层没了。**（这条依然成立，只是本案里
   底层"看不见"按键事件，所以用不上。见坑 21.5）
5. **时间戳要用事件里的，不要用收到的时刻。**
   任何"计算持续时间"的场合都一样：用数据自带的时刻，
   别用你的处理时刻 —— 处理延迟会污染结果。
6. **★ 「短按能用」推不出「长按也能用」。**
   两者走的代码路径可能完全不同（详见坑 21.8）。
   验收时要把每条路径**单独**试一遍，别用一个的成功去覆盖另一个。

### 坑 21.8：深度休眠会"吃掉"长按电源键的菜单 ★★

这是坑 21 的**第二次校正**，也是整个退出路径问题上最深的一层。

#### 现象（真机实测）

对比实验做得很干净，结论毫不含糊：

| 状态 | 长按电源键 6 秒 |
|---|---|
| **不跑看板**（重启后停在原生界面） | ✅ 正常弹出菜单：**重启 / 取消 / 熄屏** |
| **看板正在运行** | ❌ 整屏闪一下 → **全黑** → 无任何后续 |

再补两个数据点：

- 不跑脚本时，长按 **10 秒以上** → **跳过菜单直接重启**
- 看板运行时长按 8 秒 → 只有"闪一下 + 全黑"

#### 第一层误判（我犯过的错）

坑 21 里我得出过"只停 `lab126_gui` + `webreader`、留 framework
就能保住电源键"的结论，并且在文档里写成了"长按 → 弹重启菜单"。

**这个结论是错的。** 错在推理方式：

> 我看到"短按能休眠/唤醒"就以为"长按也能弹菜单"，
> 但这两件事**根本不是同一个机制**（见下面的分析）。
> 一个成功不能用来推断另一个也成功。

#### 真正的原因：设备在 `mem` 里

看板的核心机制之一（`loop()` 里）：

```sh
if setup_alarm; then
    sleep 5
    echo mem > /sys/power/state     # ← 元凶在这一行
```

设备绝大部分时间处于 **`echo mem` 深度休眠**。而：

> **在 suspend 状态下，powerd 对电源键的解释是「唤醒」，
> 不是「长按 → 弹 UI 菜单」。**

于是你按住 8 秒，系统实际做的是：
**在 suspend 里被按键唤醒 → 醒来 → `loop()` 发现被唤醒 →
检查退出 → 拉图 → 又 `echo mem` 睡回去**。

屏幕"闪一下"是这一轮刷新的刷新动作，"全黑"是重新进入 suspend
之后的屏态。**整个过程中根本没有"弹菜单"这个环节。**

#### 两个细节帮你确认这个诊断

1. **屏幕是全黑，不是保持看板图。**
   如果只是"菜单被 UI 层压住"，看板图应该还在屏幕上。
   全黑说明设备**真的执行了 suspend**。
2. **不跑脚本时菜单完全正常（三项齐全）。**
   说明系统原生功能没坏、framework 没坏、`lab126_gui` 也没坏 ——
   **唯一变量是"跑不跑看板"，也就是"有没有进 suspend"**。

#### 这是取舍，不是 bug

| 想要 | 需要 | 冲突点 |
|---|---|---|
| 续航几个月 | 尽快进 `mem` 深休眠 | **设备要"睡"** |
| 长按弹 UI 菜单 | powerd 保持活动、UI 层可用 | **设备要"醒"** |

两者在**"设备是否处于 suspend"**这一点上直接对立，没有两全解。

**我们的选择：保休眠。** 理由：看板是**放着看的**，
不需要频繁重启；而休眠是续航的根本（去掉它，KPW3 从几个月掉到几天）。

所以正确的使用方式是：

> **想重启 → 先退出看板（网页按钮 / `;log stopdash`）→
> 回到原生界面再长按电源键。**

#### 别试图"修"这个

如果把 `echo mem` 换成普通 `sleep`，菜单确实会回来，但：

- 设备不再 suspend，CPU/内存持续供电
- 续航从"几个月"掉到"几天"
- 需要常插电 —— 那就失去了"墨水屏看板"的意义

#### 教训（可复用）

1. **★ 电源键在不同电源状态下的语义可能不同。**
   "长按弹菜单"是 **OS 运行中**的行为；设备 suspend 后，
   同一个物理动作被解释成"唤醒"。**别在 suspend 场景下
   假设按键语义跟在正常运行时一样。**
2. **★ 「短按能用」推不出「长按也能用」。**
   它们可能走完全不同的代码路径（这里是：短按走 powerd 的
   休眠控制，长按走 UI 层的菜单渲染）。
   **每条路径都要单独验收**，不能用一条的成功覆盖另一条。
3. **★ 全局机制会否决局部修复。**
   坑 21 的修复（留 framework）是**局部**的；
   但 `echo mem` 是**全局**的电源状态。
   全局状态一变，局部修复就失效了。
   **排查时要顺着"谁改变了全局状态"往上找。**
4. **★ 对比实验比推理可靠。**
   "不跑脚本 - 有菜单 / 跑脚本 - 没菜单"这一个对照，
   直接锁定了变量。如果不做这个对照，
   很可能一直在 `lab126_gui` / framework / 键盘这些旁枝上打转。
5. **★ 用一个"信号"区分两种失败模式。**
   "屏幕全黑" vs "屏幕还是看板图"——
   前者是 suspend（电源状态问题），
   后者是 UI 被压（图层问题）。
   **找一个能区分假设的观察点，比多试几次更有价值。**

### 坑 22：退出路径要留两条，还要考虑"设备在睡觉"

坑 21 解决了"人在设备旁边怎么出来"。但还有个场景没覆盖：
**人不在旁边 / 懒得碰设备，想远程让它退。**

直觉做法是"服务端加个按钮，点了设备就退"。但这里有个物理限制：

> **Kindle 大部分时间在 `echo mem` 深度休眠。**
> 休眠期间它**收不到任何指令** —— CPU 停了，没有进程在跑。

所以"点了立刻退"是不可能的。最后的设计是**下次醒来时生效**：

```
网页点「退出看板」          → 服务端落盘 quit=1
用户按一下电源键            → 硬件唤醒（不需要任何软件支持）
设备醒来第一件事：查 quit    → 看到 true 就退出、还回原生界面
退出后 ack 服务端            → quit 复位为 0
```

**几个不能省的细节**：

1. **退出后必须 ack（复位）**。
   否则下次启动看板，一查又是 `quit=true`，**立刻又退出去** ——
   表现是"看板再也起不来了"，而且很难联想到是上次退出没清干净。
2. **请求状态要落盘，不能放内存变量**。
   服务重启（改配置、`systemctl restart`）会清掉内存状态。
   用户点了退出、结果因为服务重启没生效，这种事没法解释。
   落盘成文件，重启也在。
3. **查询失败一律当成"不退出"**。
   网络抖一下就退出看板，那太脆弱了。只有**明确读到** `quit=true` 才退。
   同理，解析不出来也当不退出 —— 失败方向要选安全的那一侧。
4. **判断 `quit` 不能做粗糙的字符串包含匹配。**

   ```sh
   # ❌ 会误判
   case "$body" in
       *'"quit"'*true*)  exit 0 ;;   # 看这行：{"quit": false, "note": "true"}
   esac                              # 含 "quit" 也含 "true" → 误判为要退出
   ```

   必须**先定位到 `quit` 字段本身**，再单独看它的值：

   ```sh
   # ✅ 只在 quit 的值上做判断
   _tail=$(printf '%s' "$_body" | sed -n \
       's/.*"quit"[[:space:]]*:[[:space:]]*\([a-z]*\).*/\1/p')
   case "$_tail" in true) return 0 ;; *) return 1 ;; esac
   ```

5. **写操作（退出）必须鉴权，即使读操作没鉴权**。
   `/dashboard.png` 是只读的，被陌生人看到无非是隐私问题；
   `/control/quit` 是**写操作**，接口一敞开，任何人都能远程关掉你的看板。
   所以：读接口没 token 可以放行，写接口没 token **一律拒绝**。

**教训（可复用）**：

1. **有休眠的终端，指令要"存下来等它醒"，而不是"指望立刻送到"。**
   这是所有低功耗 IoT 的通用模式（MQTT 的 retained 消息、
   各类推送的离线队列，本质都是同一件事）。
2. **状态复位（ack）和状态设置同样重要。**
   只写不复位，等于给系统埋了个"开机即触发"的雷。
3. **解析结构化数据时，永远不要用子串匹配。**
   `grep 'quit.*true'` 这种写法看起来能用，实际会被字段顺序、
   值里的内容、无关字段坑到。**定位到字段，再取它的值。**
4. **安全策略要按"读/写"分级，不是一刀切。**
   一刀切的结果通常是：要么安全到没法用，要么方便到不安全。

### 坑 23：凭证"只需要填一次"其实要求很高的技术

坑 22 的服务端遥控要一个 token。直觉是"告诉用户 export 一下就行"。
**在 Kindle 这个场景下，这条路根本走不通**，而且失败得很安静。

**问题一：`;log runme` 不是在 shell 里跑的。**

从搜索框执行 `;log runme` 时，你不是在一个交互式 shell 里 ——
**没有任何地方可以 export**。所以"让用户先 export 再跑"这种说法，
在这个入口下**物理上不成立**。

**问题二：后台守护的环境变量必须显式转发。**

`dashboard.sh` 的 `start` 分支是这么拉后台的：

```sh
( trap '' HUP; "$0" _loop ) >/dev/null 2>&1 &
```

这行是**自己写死的**，不会读取 `export` 过的环境变量。
只 export 不转发 = 守护进程收不到。

**问题三（最阴）：症状看起来跟 token 完全无关。**

拉图和查退出是两条独立请求：

| 请求 | token 从哪来 | 配错 token 的表现 |
|---|---|---|
| `/dashboard.png` | **URL 参数**（每次请求现拼） | 图拉不到，**一眼就发现** |
| `/control/status` | **环境变量**（要正确转发） | 图**照常显示**，只有退出按钮没反应 |

所以症状是「**看板一切正常，只有网页那个按钮点了没反应**」。
这几乎不可能让人联想到"token 没传进后台进程"，
只会怀疑是不是休眠、是不是按钮写错了。

**解法：把凭证落成文件，配一次永久生效。**

Kindle 端固定读 `/mnt/us/dashboard/config.env`：

```sh
CONF=$DASH_DIR/config.env
if [ -z "$TOKEN" ] && [ -f "$CONF" ]; then
    TOKEN=$(sed -n 's/^[[:space:]]*DASH_ACCESS_TOKEN[[:space:]]*=[[:space:]]*\(.*[^[:space:]]\)[[:space:]]*$/\1/p' "$CONF" | tail -n 1)
    case "$TOKEN" in                    # 去掉有人习惯加的引号
        \"*\") TOKEN=$(printf '%s' "$TOKEN" | sed 's/^"//; s/"$//') ;;
        \'*\') TOKEN=$(printf '%s' "$TOKEN" | sed "s/^'//; s/'$//") ;;
    esac
fi
```

然后**两次调用都显式带上**：

```sh
DASH_SERVER="$SERVER" DASH_ACCESS_TOKEN="$TOKEN" sh "$DASH_SH" once
DASH_SERVER="$SERVER" DASH_ACCESS_TOKEN="$TOKEN" sh "$DASH_SH" start
```

`sed` 的写法要能扛住各种手写习惯，实测覆盖了 11 种：

- 标准 `KEY=value`
- 引号包裹（单/双）
- 等号两侧空格、值后尾随空格
- 注释行、空行
- 混在多项配置里
- **CRLF 行尾**（Windows 记事本存的）★
- 重复出现时取最后一个
- 简写：只有一行的 `token` 文件

**顺带补一条自检**：`runme.sh` 启动完主动探一次 `/control/status`，
把结果直接写进日志：

```
遥控通道自检：OK（网页「退出看板」按钮可用）
```

**不主动测的话，你只有等真正想退出时才发现配错了** ——
那会儿人可能不在设备旁，正是最需要遥控的时候。

**教训（可复用）**：

1. **"告诉用户 export 一下"是个危险的默认假设。**
   先问：**用户是在什么环境里执行这个脚本？** 有没有 shell？
   没有 shell 的入口（搜索框、计划任务、桌面快捷方式、双击运行）
   **读不到任何环境变量**，凭证必须落文件。
2. **不同请求走不同的凭证通道，是配错时最难查的一类问题。**
   同一个 token，一条走 URL、一条走环境变量 ——
   错了以后只有一半功能坏掉，"一半好一半坏"会把人往错误方向带。
   **同类凭证尽量统一走同一条通道**，或者启动时就自检一遍。
3. **用户模板里的占位符不能用中文。**
   给用户的 `config.env` 模板如果写 `DASH_ACCESS_TOKEN=在这里填`，
   照抄不改的话这串中文会被当真 token 发进 HTTP header ——
   非 ASCII 在 header 里会编码失败，报错完全指不到病根。
   模板用 `<PUT_TOKEN_HERE>` 这种 ASCII 尖括号占位符，
   并在脚本里**主动识别并拒绝**（含 `<`/`>` 或非 ASCII 一律当未配置）。
   > 这条之前已经在配置模板上吃过一次亏，这是第二次 ——
   > 凡是"给用户填空"的地方都要按这个标准检查。
4. **凭证要用"能不能用"来判断，不是"填没填"。**
   日志里写「token 已配置（长度 36）」是不够的 ——
   长度对但值错，照样 401。要真发一次请求验证，把结果写出来。

### 坑 24：浏览器里预览图躺倒 —— 别用 CSS 反旋

`/dashboard.png` 输出的是**竖图**（1072×1448），因为 `eips` 不认旋转、
只负责贴图，方向必须服务端先转好（坑 14）。
但浏览器里人要看**横的**，所以预览页得把图转回来。

一开始的做法是 CSS 反旋：

```css
img { transform: rotate(-90deg); width: 100vh; height: auto; }
```

**实测不管用** —— 预览页每 60 秒换一次图，靠 `img.src = ...` 刷新：

```js
setInterval(() => { img.src = '/dashboard.png?t=' + Date.now() ... }, 60000);
```

改 `src` 会触发重排，**旋转就在这一步丢掉**，页面变成躺倒的。
期间试过几个方向都不行：

- 把 `<style>` 块移到 `<img>` **前面** —— 无效
- 改成**内联 `style` 属性**（优先级最高、不依赖 DOM 顺序）—— 仍然躺倒
- 加 `transform-origin` / `flex-shrink` / 调 `align-items` —— 无效

**根因是思路方向错了**：把"图像方向"这个**数据层面的属性**
交给**表现层（CSS）**去修正，本身就脆弱 ——
任何一次重排、任何一个渲染阶段差异都可能把它冲掉。

**改成服务端直接给摆正的图**，加一个开关参数：

```python
@app.get("/dashboard.png")
def dashboard_png():
    rot_raw = request.args.get("rot")
    rotate = None                      # None = 跟配置（Kindle 要竖图）
    if rot_raw is not None:
        rotate = rot_raw not in ("0", "false", "no")
```

- **Kindle** 请求 `/dashboard.png` → 竖图（不变，一行没动）
- **预览页** 请求 `/dashboard.png?rot=0` → 横图

`Renderer.render()` 也加了对等的参数：

```python
def render(self, p: Payload, rotate: bool | None = None) -> Image.Image:
    if rotate is None:
        rotate = self.rotate     # 默认跟配置，保持向后兼容
    ...
    if rotate:
        img = img.transpose(2)
```

**两份缓存要分开**。预览那份不走电量分桶，
如果和 Kindle 那份共用同一个 `_png_cache`，会互相冲掉 ——
表现是"浏览器看到竖图"或者"Kindle 拿到横图"。
所以预览单独一个 `_png_rot_cache`。

代价是同一帧渲染两次（各留一份缓存），几十毫秒，可以忽略。

**断言了两个方向都对**：

```
Kindle 路径    : (1072, 1448) L     ← 没变，eips 要的就是这个
预览横图路径   : (1448, 1072) L     ← 浏览器看这个
```

**教训（可复用）**：

1. **"数据方向"的问题要在数据层解决，别推给 CSS。**
   旋转、缩放、镜像这类**图像固有的属性**，
   在生成阶段一次性定好，比让浏览器/客户端每次渲染时修正可靠得多。
   CSS 变换适合"展示层的选择"（缩放适配、hover 动效），
   不适合"纠正数据本身的朝向"。
2. **动态换 `src` 的元素，别依赖 CSS 变换。**
   重排会让变换失效，而且失效方式**在不同浏览器/时机下不一致** ——
   表现为"有时候是好的"，最难查。
3. **给一个已有接口加参数时，默认值必须保持老行为。**
   `rotate=None` → 跟配置，Kindle 端一行代码都不用改。
   要是默认设成 `False`，Kindle 直接拿到横图、屏幕全错。
4. **派生出的第二份数据，缓存要分开。**
   共用一份缓存 = 两个用途互相踩，而且症状是"偶发"的。

### 坑 25：用固定 `sleep` 等外部条件 ★

**现象**：设备端日志里拉图失败率约 **1/3** —— 不报错，就是没拉到，
下一轮又好了。看起来非常像"网络不稳"，容易误判成 WiFi 质量差。

**根因**：等 WiFi 就绪用的是写死的 `sleep 8`。

```sh
wifi_on() {
    lipc-set-prop com.lab126.wifid enable 1
    sleep 8        # ← 不管好没好，都等满 8 秒
}
```

问题在于**就绪时间本来就不确定**：

| 实际情况 | `sleep 8` 的后果 |
|---|---|
| 1 秒就连上 | 白等 7 秒 |
| 十几秒才连上（刚唤醒、信号弱） | 8 秒不够，请求打空 → **这一轮白费** |

固定值只在"实际耗时**恰好稳定**且小于该值"时才不出错，
而这个前提在**唤醒 + 无线重连**这种场景下根本不成立。

**修法：改成「轮询探测」—— 通了就走，超时才放弃。**

```sh
wait_for_wifi() {
    _i=0
    while [ "$_i" -lt "$WIFI_WAIT_MAX" ]; do
        ping $PING_OPTS "$WIFI_TEST_IP" >/dev/null 2>&1 && return 0
        _i=$((_i + 1))
        sleep 1
    done
    return 1
}
```

（参考 pascalw/kindle-dash 的 `src/wait-for-wifi.sh`）

**三个设计要点**：

1. **探测目标选「公共 IP」而不是「自己的服务端」** ——
   这样才能区分「本机没网」和「网通但服务端挂了」，
   日志里直接写清是哪种，排查少走一半弯路。
2. **探测失败不应该中断主任务** —— 万一那个 IP 恰好不通，
   但服务端其实能访问（同机房、内网），跳过就亏了。
   所以返回值**只用来记日志区分故障类型，不做门禁**。
3. **`ping -W` 要先探测兼容性** —— busybox 版本差异大，有的没编 `-W`。
   先 `ping -c 1 -W 1 127.0.0.1` 试一下，不行就退回不带 `-W`。

**教训（可复用）**：

1. **★ 等外部条件要用「轮询 + 超时」，不要用固定 `sleep`。**
   固定值隐含假设「耗时稳定」，而凡是涉及**网络、硬件初始化、
   外部服务**的等待，这个假设都不成立。
   写成「每 N 秒探一次，探到就继续，最多等 M 次」——
   既不白等，也不会不够。
2. **探测要探「这件事本身」，别用代理指标做门禁。**
   这里真正要的是"能连上我的服务器"，探的却是"能 ping 通公共 IP"。
   两者**不等价**，所以探测结果只能当**参考**，不能当**开关**。
3. **★ 分清「等它好」和「踢它一脚」两种修复 —— 不能混用。**
   - **等它好**（轮询探测）→ 治"还没就绪"，**每轮都该做**
   - **踢它一脚**（toggle 重连）→ 治"卡死在坏状态"，**只在连续失败后做**

   混在一起的后果：要么每轮都白折腾一次重连，
   要么对着一个"永远好不了"的状态干等。
4. **★ 还要再细分：「压根没连上」和「连上了但不通」是两回事 ——
   但只用于决定「要不要继续等」，不能用来决定「要不要修复」。**
   - **压根没连上**（内核报 `Network is unreachable`）→
     等下去没意义（网络源都不在），应该**立刻放弃等待**。
   - **连上了但不通**（探测超时）→ 才值得等满上限。

   **区分方法**：把探测命令的 **stderr 也收进来**，看有没有
   `unreachable` 字样。一行 `case` 就够。

   实例：这台设备的网络源是**手机热点**。热点一关，内核立刻报
   unreachable。不区分的话，每轮白等满 30 秒
   （10 分钟一轮 → 一天白醒 72 分钟）。

   > ⚠️ **但别把「不等待」和「不修复」混为一谈**（我在这里栽过一次）：
   > 我一开始推断「热点不在 → toggle 也没用 → 不该触发自愈」，
   > 结果用户实测发现：**热点恢复后设备并不会自己重连，
   > 必须插拔一次 USB 才恢复**。
   > 关键点是：「网络源不在」和「网络源在但设备卡住」**从内核角度看
   > 完全一样**（都是 unreachable），根本无法区分。
   > **结论**：该不该**等**可以按 unreachable 判断；
   > 该不该 **toggle** 不能 —— 修复动作必须覆盖两种情况。
   > 因为 toggle 的代价很小（10 秒），而漏掉一种的代价是"永远连不上"。
   > **「诊断细粒度」≠「修复细粒度」：诊断可以分得很细，
   > 但修复动作要偏向"宁可多踢一脚"。**

### 补充：一次绕远路的排查复盘

有个坑值得单独说，因为它暴露的是**方法论**问题，不是技术问题。

**背景**：服务起不来，`systemctl status` 显示
`failed (Result: start-limit)` / `status=1/FAILURE`。
而**恰好**在那之前我刚改过渲染代码（加了图片旋转），于是很自然地把
两件事关联起来 —— "是不是我改的东西有问题？"

然后就开始猜：Pillow 版本？API 兼容性？Python 3.9 语法？
前后猜了五六种可能，逐一在本地验证，
**每一个都排除了，而服务还是起不来。**

**真相**：`journalctl` 的**完整输出**里，第一行就写着

```
渲染自检通过: 1072x1448 L        ← 我的代码明明跑通了
Address already in use           ← 真正原因：端口被占
```

之所以没早看到，是因为我只看了 `systemctl status` 的**摘要**
（它只告诉你"进程以 1 退出"，不告诉你为什么），
而没有第一时间翻**应用的完整日志**。

**三条可复用的原则**：

1. **先取证，再假设。** 报错日志是证据，
   猜是假设。证据没拿到之前，所有假设都是在浪费轮次。
2. **看最内层、最完整的日志，别看外层摘要。**
   systemd 摘要 → 应用日志 → 应用前台运行，
   一层层往里剥，越往里信息越精确。
3. **警惕"时间上相邻"的归因。** 改动和故障时间接近，
   只是**相关**，不是**因果**。这个案例里，
   先入为主的归因（"我刚改了代码"）直接带偏了整个排查方向。

**"本地验证通过"不等于"服务器没问题"** —— 本地 Python 3.13 + Pillow 12，
服务器 Python 3.9 + Pillow 11，环境本就有差异，
所以本地的排除结果**不能反证服务器正常**。这种情况下更应该优先
拿服务器上的原始报错，而不是靠本地模拟去猜。
